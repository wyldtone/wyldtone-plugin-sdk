# Faust -> Wyldtone WASM plugins

The third SDK backend compiles `.dsp` code with Faust's C++ backend, embeds the
produced DSP class into a Wyldtone C++ ABI wrapper, then uses the **existing**
Emscripten builder, WASM inspector, DSP parameter probe, WAP packager, and benchmark.
Neither the audio engine nor the WAP format needs to change.

## Quick start on the Debian build host

From a checkout of the SDK repository:

```bash
sudo docker compose build sdk                 # Faust is installed in the Docker image
sudo docker compose run --rm sdk versions      # check compiler versions
sudo docker compose run --rm sdk test          # Cargo test
sudo docker compose run --rm sdk build examples/faust_gain/plugin.config.json
```

Expected outputs:

```text
examples/faust_gain/build/wyldtone/
  faust_generated.cpp    # generated by Faust; rebuildable
  faust_wrapper.cpp      # generated by SDK; rebuildable
  plugin.wasm
  manifest.json
  dsp-test-report.json   # auto-generated by default
  Faust-Stereo-Gain.wap
```

For a quick first compile without the parameter probe:

```bash
sudo docker compose run --rm sdk build examples/faust_gain/plugin.config.json --skip-dsp-test
```

To explicitly repeat an isolated parameter test or run the benchmark:

```bash
sudo docker compose run --rm sdk test-dsp examples/faust_gain/build/wyldtone/plugin.wasm --profile balanced
sudo docker compose run --rm sdk benchmark examples/faust_gain/build/wyldtone/plugin.wasm --reference-id wyserver-v1
```

## Creating your own Faust effect

Create a directory with `plugin.config.json` and a `.dsp` file:

```json
{
  "id": "org.example.myfaust",
  "name": "My Faust Effect",
  "manufacturer": "Example",
  "version": "0.1.0",
  "category": "Drive",
  "faust": { "source": "effect.dsp" },
  "audio": { "inputs": [2], "outputs": [2] }
}
```

`faust.source` must be a relative `.dsp` path inside the plugin folder.
Specify exactly **one** backend (`cpp`, `juce`, or `faust`).

The bridge reads **active** Faust UI widgets (sliders, numerical entries,
buttons, checkboxes) and generates host automation parameters. Parameter IDs
are normalized from the Faust UI group path and label. Keep those names stable
once users start storing presets. `unit` metadata is sent as parameter label.
The bridge preserves the Faust value ranges and normalizes the ABI get/set
methods to 0..1. Passive bargraphs are not host parameters.

## Supported today / limitations

* One main input bus and one main output bus: 0/1/2... channels as declared;
  each bus is limited to 8 channels in this first adapter. Audio metadata must
  match `getNumInputs()` and `getNumOutputs()` of the compiled Faust DSP.
* The general Wyldtone audio ABI still has a 16,384-float shared buffer. The
  bridge additionally limits one processing call to at most 2,048 frames.
* Faust C++ runs inside WASM, **without browser threads**. This does not add
  thread support or native Faust audio drivers.
* Controls are built at initialization. No allocations occur in `compute()`
  on the bridge side; third-party Faust code must still be audited for RT safety.
* Soundfile widgets, MIDI, multiple sidechain buses, sample-accurate parameter
  automation, custom state blobs, and exposed passive bargraph meters are not
  yet supported. Do not silently assume such Faust programs work unchanged.
* Faust `style:menu` / enumerations are not yet translated to Choice metadata;
  they are exposed as ordinary numeric controls in this first version.
* The implementation uses the generated DSP class rather than Faust's direct
  WebAssembly backend, because it must implement Wyldtone's existing ABI.
* Developer-provided `faust` compiler version should be recorded when
  publishing; the container reports its installed version in `versions`.
* `plugin_init()` initializes at the actual sample rate supplied by Wyldtone.

## Troubleshooting

* `Required build tool not found: faust`: rebuild image with
  `sudo docker compose build sdk` after copying `docker/Dockerfile`.
  The Faust Debian/Ubuntu package may need the `universe` repository on Ubuntu.
* `Faust C++ code generation failed`: run `docker compose run --rm sdk shell`
  then inspect the Faust compiler errors in the `.dsp` file.
* `WASM bus layout ... differs`: set `audio.inputs` and `audio.outputs` to the
  actual inputs and outputs of your `process` expression.
* `WARN: ... no observable change`: see [dsp-tests.md](dsp-tests.md) for
  contextual parameter checks and the limits of silent-output comparisons.
* Large effects can be slow even when valid. Use `benchmark` separately;
  benchmark results are reference-machine dependent, not portable CPU promises.

The SDK's new bridge and architecture are original SDK code; license them under

license does not, by itself, force generated plugins to be open-source.
However, the licenses of the *Faust source*, imported `.lib` files, generated
architecture material, and any bundled third-party source must be checked
before redistributing a plugin. See the Faust documentation FAQ on generated
code licensing. <https://faustdoc.grame.fr/manual/faq/>

The `faust_gain` example is built end-to-end in the SDK GitHub Actions CI with
Faust and Emscripten, then processed by the offline WAP reference host.
The automated audio test compares stereo sample-level RMS at -24 dB, 0 dB and
+12 dB, including the generated parameter ID. This validates the reference
example in CI, **not** every Faust plugin or an end-to-end deployment on an
individual developer's server.
